# Motion Tracker — прототип трекинга движений по камере (ПК)

## Что строим

Десктопный прототип: веб-камера ноутбука → модель позы → координаты тела → отрисовка поверх видео в реальном времени. Главный визуальный элемент — два круга на руках. Игр пока нет.

Это первая ступень. Следующие: Android (Kotlin + CameraX), затем iOS. Поэтому код делится на слои с переносимым контрактом (см. «Архитектура»): логику без камеры и без модели потом переписываем на Kotlin почти дословно.

## Вне рамок (не делать без явной просьбы)

- Игры вне пакета `game/` и его этапов G (см. «Мини-игры»).
- Обучение или дообучение моделей: используем только готовую.
- Сервер, сеть, передача видео куда-либо: всё считается локально. Исключение — VR-мост (этапы V): только координаты рук по UDP на `127.0.0.1`, без видео.
- Распознавание жестов (Gesture Recognizer). Пальцы (Hand Landmarker) — только в рамках этапа 6.
- GUI-фреймворки (Qt, Tkinter, pygame): окно только средствами OpenCV.
- Код под iOS. Android — только по разделу «Android» ниже.

## Стек

- Python 3.11 или 3.12. MediaPipe заявляет поддержку 3.9–3.12, на 3.13+ не ставить.
- `mediapipe`, только Tasks API: `mp.tasks.vision.PoseLandmarker`.
- `opencv-python`: камера, окно, рисование.
- `pytest`: тесты чистой логики.

Запрещено использовать `mp.solutions.*`, включая `mp.solutions.drawing_utils`. Этот legacy API удалён из пакета начиная с 0.10.31, но на нём написано большинство старых туториалов. Код оттуда не копировать, рисовать самим через `cv2`.

Перед использованием незнакомого вызова MediaPipe сверяйся с установленной версией (`python -c "import mediapipe as mp; print(mp.__version__)"`) и с официальным гайдом: https://ai.google.dev/edge/mediapipe/solutions/vision/pose_landmarker/python

## Модель

- Файл `pose_landmarker_full.task` лежит в `models/`, в git не коммитится.
- URL: https://storage.googleapis.com/mediapipe-models/pose_landmarker/pose_landmarker_full/float16/latest/pose_landmarker_full.task
- Если URL не отвечает, взять актуальный из раздела Models: https://ai.google.dev/edge/mediapipe/solutions/vision/pose_landmarker
- Варианты lite, full, heavy переключаются через конфиг, по умолчанию full.
- Модель отдаёт 33 точки. Нужные индексы: 0 нос; 11/12 плечи; 13/14 локти; 15/16 запястья; 17/18 мизинцы; 19/20 указательные пальцы; 23/24 бёдра; 25/26 колени; 27/28 лодыжки. Нечётный индекс — левая сторона человека, чётный — правая.

## Архитектура

Конвейер: `capture → tracker → smoothing → renderer`.

Контракт между слоями (`motion/contract.py`, без импортов `mediapipe` и `cv2`):

```python
@dataclass(frozen=True)
class Landmark:
    x: float           # 0..1 по ширине кадра, может выходить за пределы
    y: float           # 0..1 по высоте кадра
    z: float           # глубина относительно бёдер, меньше = ближе к камере
    visibility: float  # 0..1

@dataclass(frozen=True)
class PoseFrame:
    timestamp_ms: int                        # момент захвата кадра
    landmarks: tuple[Landmark, ...] | None   # 33 точки или None, если человека нет
```

Правила слоёв:

- `mediapipe` импортируется только в `tracker.py`.
- `cv2.VideoCapture` используется только в `capture.py`, рисование `cv2.*` только в `renderer.py`.
- `contract.py`, `geometry.py`, `smoothing.py` — чистый Python без внешних зависимостей.
- Список связей скелета хранится в `contract.py` как свой список пар индексов, из `mediapipe` не берётся.
- Все настраиваемые числа лежат в `config.py`, а не в коде слоёв.

## Обязательные технические решения

- **Режим**: `RunningMode.LIVE_STREAM` с `result_callback`, кадры отправляются через `detect_async(mp_image, timestamp_ms)`.
- **Потоки**: callback вызывается из потока MediaPipe. В нём только преобразование результата в `PoseFrame` и запись в переменную под `threading.Lock`. Никакого рисования и `cv2.imshow` в callback: всё это в главном цикле.
- **Метки времени**: `timestamp_ms` должен строго возрастать. Брать из `time.monotonic()`, при совпадении с предыдущим кадр пропускать.
- **Очередей нет**: если модель занята, `detect_async` сам отбрасывает кадр. Это нужное поведение, буфер кадров не строить.
- **Цвет**: OpenCV отдаёт BGR, `mp.Image` ждёт RGB (`mp.ImageFormat.SRGB`). Конвертировать перед инференсом.
- **Зеркало**: инференс идёт по исходному, не отражённому кадру, чтобы «левая» и «правая» рука оставались анатомически верными. Для показа кадр отражается по горизонтали, а координата пересчитывается как `x → 1 - x` в `geometry.py`.
- **Сглаживание** применяется один раз на каждый новый `PoseFrame` (по смене `timestamp_ms`), а не на каждый отрисованный кадр. Шаг времени фильтра берётся из `timestamp_ms`.
- **Камера на Windows**: открывать как `cv2.VideoCapture(0, cv2.CAP_DSHOW)`, запрашивать 1280×720 и проверять фактическое разрешение.
- **Зависимости**: сначала ставится `mediapipe`, затем проверяется `python -c "import cv2"`. `opencv-python` ставить, только если `cv2` не импортируется: две сборки OpenCV в одном окружении конфликтуют. Версию `numpy` вручную не фиксировать. После установки выполнить `pip freeze > requirements.txt`.

## Инженерные правила

### Scope
- Отслеживается один человек: `num_poses=1`. Несколько людей, жесты, пальцы, идентификация — только отдельным этапом.
- Абстракции «на будущее» не создавать: слой, класс или интерфейс появляется, только если нужен текущему этапу.

### Координаты
- Три пространства: пиксели исходного кадра камеры; нормализованные координаты MediaPipe; координаты отображения.
- `tracker.py` работает только с исходным, незеркальным кадром.
- Все преобразования координат, включая `x → 1 - x`, только в `geometry.py`. `renderer.py` координаты не исправляет и не зеркалит.
- Отражение самой картинки (`cv2.flip`) делает `renderer.py`: это операция над изображением, не над координатами.

### Состояние позы
- `PoseFrame` — результат конкретного запуска модели. Поза не найдена → `landmarks = None`. Старые landmarks как новый результат не выдаются.
- Сглаживание не меняет исходный `PoseFrame`, а создаёт новый.
- Если поза потеряна дольше `FILTER_RESET_MS` (`config.py`), состояние фильтров сбрасывается, чтобы при возвращении человека не было интерполяции от старой позиции.
- Удержание круга при потере точки (`LOST_HOLD_MS`) — чистая логика в `geometry.py` с тестами.

### Confidence
Параметры MediaPipe не смешивать, в `config.py` они раздельны: `POSE_DETECTION_CONFIDENCE`, `POSE_PRESENCE_CONFIDENCE`, `TRACKING_CONFIDENCE`, `LANDMARK_VISIBILITY_THRESHOLD`. `visibility` точки решает только, можно ли использовать эту точку.

### Ресурсы и ошибки
- `cv2.VideoCapture`, `PoseLandmarker` и окна OpenCV закрываются даже при исключении (`try/finally` или context manager).
- Фатальные ошибки запуска (камера не открылась, модели нет, модель не загрузилась, нет зависимости) → понятное сообщение и ненулевой exit code.
- Ошибка чтения одного кадра не даёт traceback: кадр пропускается. После `MAX_READ_FAILURES` (`config.py`) неудач подряд — выход с сообщением и ненулевым кодом.
- Голый `except Exception: pass` запрещён.
- Преобразование результата в `PoseFrame` не зависит от типов MediaPipe (достаточно объектов с `.x .y .z .visibility`), чтобы тестироваться без модели.

### Производительность
- Приоритет — realtime. Без очереди кадров, без тяжёлой работы в callback, без лишних копий кадров.
- Оптимизация: сначала измерить, потом менять.
- Ориентиры (не критерии до этапа 4): render FPS ≥ 30, tracking FPS ≥ 20, медианная задержка < 100 мс.

### Изменения кода
- Перед этапом `git status`. После: тесты, проверка списка изменённых файлов, без случайных изменений, один логический коммит этапа.
- Большой рефакторинг не совмещать с новой функциональностью.
- Если этап требует изменить архитектурное решение из этого файла — сначала сообщить и объяснить, не менять молча.

### Жесты и события
Каталог и архитектура распознавания: `docs/MOTION_GESTURES_SPEC.md`. Перед работой над жестом читать его раздел.
- Сначала MVP-набор (§62), не весь каталог.
- Различать state (держится, пока условие истинно), transition (один раз при смене state) и action (по истории кадров).
- Debounce, гистерезис (разные пороги входа и выхода), cooldown — числа в `config.py`.
- Расстояния нормализовать: кисть — `dist(wrist, middle_mcp)`, тело — ширина плеч.
- Потеря трекинга — `*_CANCELLED`, а не `*_RELEASED`/`*_ENDED`.
- Логика жестов не зависит от классов MediaPipe; приложение получает события, а не landmarks; смысловые действия (NEXT, SELECT) — отдельный слой маппинга.
- Осознанное отличие от §3.2: сторона кисти берётся по ближайшему запястью позы, а не по handedness Hand Landmarker (handedness путается на крупных планах). Handedness — только запасной вариант, когда позы нет.

## Этапы

Идти строго по порядку. Следующий этап не начинать, пока я не подтвердил критерии текущего.

### Этап 0. Каркас
Окружение, зависимости, `scripts/download_model.py`, `.gitignore`, окно с камерой и счётчик FPS, выход по `q` или `Esc`.
**Готово, когда:** `python -m motion` показывает зеркальное видео и FPS; после выхода процесс завершается, камера освобождена.

### Этап 1. Скелет
`tracker.py` с PoseLandmarker, преобразование в `PoseFrame`, отрисовка 33 точек и связей.
**Готово, когда:** скелет совпадает с телом; я поднимаю правую руку, и она поднимается с той же стороны экрана, как в зеркале; без человека в кадре скелета нет и нет исключений.

### Этап 2. Два круга на руках
Круг на каждой руке. Центр по умолчанию — запястье; опция `palm` — среднее между запястьем, указательным пальцем и мизинцем. Точки с `visibility` ниже порога считаются потерянными: круг держится на последнем месте `LOST_HOLD_MS` (старт 200 мс), затем исчезает. Клавиша `s` включает и выключает скелет.
**Готово, когда:** круги следуют за руками; рука за спиной или за краем кадра даёт исчезновение круга без скачков в случайные места; левый и правый круг разного цвета и не меняются местами.

### Этап 3. Сглаживание
One Euro Filter на каждую координату каждой точки. Стартовые параметры: `min_cutoff=1.0`, `beta=9.0`, `d_cutoff=1.0` (классическое `beta=0.007` рассчитано на пиксели; координаты у нас 0..1, поэтому `0.007 × 1280 ≈ 9`); подбираются на глаз (дрожит в покое — уменьшать `min_cutoff`, отстаёт на быстрых движениях — увеличивать `beta`). Клавиша `f` включает и выключает фильтр для сравнения.
**Готово, когда:** при неподвижных руках круги не дрожат; при быстром взмахе отставание на глаз не заметно; тесты проходят (постоянный сигнал не меняется, шум на неподвижном сигнале уменьшается, ступенька сходится к новому значению).

### Этап 4. Метрики
Оверлей: FPS отрисовки, FPS трекинга (результатов в секунду), задержка = текущее время минус `timestamp_ms` результата (медиана за секунду, мс). Флаг `--log metrics.csv`.
**Готово, когда:** значения видны на экране; в README есть таблица замеров для lite, full и heavy на этом ноутбуке.

### Этап 5. Воспроизведение из файла (опционально)
`--input video.mp4` прогоняет тот же конвейер по видеофайлу (`RunningMode.VIDEO`, `detect_for_video`), чтобы сравнивать параметры фильтра на одинаковом входе.

### Этап 6. Пальцы
`HandLandmarker` (21 точка на кисть, до 2 кистей) в том же `LIVE_STREAM`-режиме рядом с PoseLandmarker; `mediapipe` по-прежнему только в `tracker.py`. Модель `hand_landmarker.task` в `models/`, качается тем же скриптом. В контракт добавляется структура для кистей без типов MediaPipe. Сторона кисти определяется сопоставлением с запястьями из Pose (ближайшее запястье), а не по handedness модели рук: цвета не должны меняться местами. Отрисовка суставов и связей пальцев своим списком пар, клавиша `h` включает и выключает пальцы.
**Готово, когда:** пять пальцев каждой руки отслеживаются и рисуются поверх видео; левая и правая кисть не путаются при скрещивании рук; тесты на сопоставление кистей с запястьями проходят; в README есть замер FPS трекинга и задержки с двумя моделями против одной Pose.

### Этап 7. Сцена: объекты управляются телом
`motion/scene.py` (чистый Python, координаты отображения в пикселях): шар с трением и отскоком от краёв; круги рук и кончики пальцев — коллайдеры, толкают шар с учётом скорости; щипок (кончики большого и указательного пальца вместе, порог относительно размера ладони, с гистерезисом) внутри шара берёт его, разжатие бросает со скоростью руки; кнопка вверху кадра нажимается удержанием руки внутри неё `BUTTON_DWELL_S` (дотянуться можно только поднятой рукой), нажатие возвращает шар в центр. Клавиша `g` включает и выключает сцену. Все числа в `config.py`.
**Готово, когда:** шар толкается любой рукой в сторону движения руки и не застревает в краях; появившаяся над шаром рука не выстреливает его; кнопка срабатывает один раз за удержание и показывает прогресс; тесты `tests/test_scene.py` проходят.

### Этап 8. Позы и действия
Распознавание (после этапа 9a — `body_state.py`, `action_detector.py`, `gesture_detector.py`, `event_engine.py`) поверх сглаженной позы, в изотропных координатах (`x × ширина/высота`). Позы за кадр: руки вверх, руки в стороны, наклон влево/вправо (сторона — анатомическая, как у рук), присед (угол колена). Устранение дребезга: поза включается и выключается, только продержавшись `POSE_HOLD_MS`. Действия по нескольким кадрам (state machine): прыжок (подъём плеч над скользящей базовой линией и возврат за короткое время), удар (быстрое выпрямление руки, с паузой между ударами). Активные позы и последнее событие видны на экране.
**Готово, когда:** каждая поза и действие распознаются при показе и не срабатывают в нейтральной стойке; присед не считается прыжком; тесты `tests/test_body_state.py` и `tests/test_event_engine.py` проходят.

### Этап 9. Gesture Engine по спецификации
Архитектура и каталог — `docs/MOTION_GESTURES_SPEC.md`.
**9a. Структура (без новых жестов):** раскладка по §64 — `events.py` (`State`, `EventType`, `GestureEvent` с `confidence`), `body_state.py`, `hand_state.py`, `action_detector.py`, `gesture_detector.py`, `event_engine.py` (debounce, cooldown, `GestureEngine` с входами `update_pose` / `update_hands`). Потеря руки во время щипка — `*_PINCH_CANCELLED`, шар при этом не бросается (§68). Кисти сопоставляются с позой только при разнице меток ≤ `MAX_SYNC_DELTA_MS` (§66). `motion_history.py` — в 9b, когда появятся траектории.
**Готово, когда:** поведение на экране то же, что после этапа 8 и захвата шара; все тесты проходят; потеря руки с шаром не бросает его.
**9b. Остаток MVP (§62):** состояния пальцев → `OPEN_PALM` / `FIST` / `POINT`; подъём каждой руки; появление и потеря человека и рук; `SWIPE`, `WAVE`, `CLAP`; `SQUAT_STARTED` / `SQUAT_REP`; `JUMP` + `LAND`.

### Этап 10. Кисть и руки (§63, первая часть)
`SWIPE_UP/DOWN` (траектория запястья относительно плеч, чтобы прыжок и присед не давали свайпов); `GRAB_STARTED/RELEASED/CANCELLED` (кулак с гистерезисом по числу согнутых пальцев; щипок не начинается внутри кулака); `PUSH`/`PULL` (открытая ладонь к камере / от камеры по изменению размера ладони на кадре, а не по шумному `z`); `THROW` (разжатие кулака или щипка на быстром движении руки). Шар в сцене берётся и кулаком.
**Готово, когда:** каждый жест срабатывает при показе и не срабатывает в похожих движениях (прыжок ≠ свайп вверх, удар кулаком ≠ push, разжатие на месте ≠ бросок); тесты проходят.

### Этап 10b. Формы кисти из общего списка жестов
Классификатор `hand_state.hand_shape`: сначала геометрические проверки (🤌 кончики вместе и вынесены от ладони, 👌, 🫰 касание вынесено от ладони, 🖖 зазор, 🤞 перекрещивание), затем таблица «вытянутые пальцы + большой палец» (👍👎🤘🤟🤙🖕, finger gun / L, ✊, 👆). Плюс направление указательного (`POINT_UP/DOWN/LEFT/RIGHT`, сторона анатомическая), счёт пальцев 0–5, `BOTH_HANDS_<форма>`, двуручные 🫶 и 🙏 (различаются расстоянием между запястьями), круг рукой по/против часовой стрелки на зеркальном экране. Не делаем: 🫵 в камеру (нужна точная глубина), C-shape (неотличим от полуоткрытой руки), «поднятый кулак» отдельно (это `FIST` + `ARM_UP`).

## Мини-игры (пакет `game/`)

Камера — контроллер. Отдельный пакет в этом же репозитории (не форк): игры используют конвейер трекера (`motion/pipeline.py`) и `GestureEngine`, а `motion` про игры ничего не знает. Запуск: `python -m game`.

```text
Pipeline (камера → поза + руки → сглаживание → события)
  ↓
game/player.py   PlayerState: руки, голова, корпус в игровых координатах + события и состояния
  ↓
логика режима    чистый Python: объекты, столкновения, очки (без cv2 и mediapipe)
  ↓
game/render.py   всё рисование игры (cv2)
```

Правила:
- Логика игр не видит landmarks и MediaPipe — только `PlayerState`. Её можно будет перенести в Unity/Godot.
- Игровые координаты — пиксели зеркального кадра (то, что видит игрок). Пересчёт из координат трекера — только в `player.py`.
- Окно — только OpenCV (правило «Стек» в силе); рисование — только в `game/render.py`.
- Управление без клавиатуры: старт и рестарт — жестом (обе руки вверх). Клавиши только `q`/`Esc` для выхода.
- Числа игр — в `game/config.py`. Тесты логики — `tests/test_game_*.py`.
- Общие части (очки, спавн, геометрия) выносить в отдельные модули, когда они понадобятся второму режиму, не раньше.

### Этапы G
**G1. Ловля.** Сверху падают шары с ускорением (гравитация, ~3.5 с через экран); синие ловит левая рука, красные — правая. Ловит вся кисть: каждая косточка модели рук как отрезок толщиной пальца; если модель рук потеряла кисть — контур из позы (запястье, указательный, мизинец, большой палец). Очки, комбо (множитель растёт каждые 5 подряд), жизни (промах — минус жизнь, неправильная рука — сброс комбо). Темп растёт со временем. Старт и рестарт — обе руки вверх. **Готово, когда:** играется без клавиатуры от старта до game over и рестарта; тесты логики проходят.
**G2. Типы объектов.** Бомбы (не трогать), бонусы (жизнь, замедление), разные скорости.
**G3. Fruit Ninja.** Фрукты летят снизу по дуге; разрез — когда отрезок пути кисти между кадрами пересёк фрукт со скоростью выше порога (медленно провести рукой — не разрез).
**G4. Удары по мишеням.** Мишени в зонах (голова, слева, справа, корпус); попадание — событие `*_PUNCH` в зоне мишени.
**G5. Уклонение.** Стены и проёмы; хитбокс тела из позы (голова, плечи, бёдра); наклоны, присед, прыжок.
**G6. «Повтори позу».** Показывается поза — игрок держит её N секунд (состояния `GestureEngine`).
**G7. Аркада.** Меню выбора режима жестом (удержание руки на кнопке), таблица рекордов.
**G8. Ритм-игра.** Таймлайн нот, окна попадания PERFECT / GOOD / OK / MISS по разнице времени, направление удара.
Опционально позже: бокс со state machine боя (джеб, блок, уклон).

Этапы V (Beat Saber) — после G или по запросу.

### Этапы V. Beat Saber через SteamVR

### Этап 13 (опционально). Лицо и аватар
Делается только по отдельной просьбе, после этапов V. Face Landmarker (478 точек, 52 коэффициента мимики) третьей моделью рядом с Pose и Hand; повороты и наклоны головы (§5 спецификации жестов: `HEAD_LEFT`, `HEAD_NOD`, `HEAD_SHAKE`); мимика (моргание, рот, брови); вывод позы, рук и лица по протоколу VMC (OSC), чтобы двигать VRM-аватар в программах вроде VSeeFace или Warudo — «дешёвый motion capture без костюма». Перед началом замерить FPS с тремя моделями: запас есть только на lite/full.
**Готово, когда:** аватар повторяет позу, пальцы, повороты головы и моргание; FPS трекинга с тремя моделями записан в README.

## Android

Тот же инструмент нативным приложением: Kotlin + CameraX + MediaPipe Tasks for Android. Код в `android/` этого репозитория. Python-прототип остаётся эталоном поведения: `contract`, `geometry`, `smoothing`, `metrics` переносятся почти дословно, с теми же параметрами и теми же тестами.

### Стек и тулчейн
- Тулчейн в `D:\claudendroid-tools`: JDK 17, Gradle 8.10.2, Android SDK (platform 35, build-tools 35), эмулятор.
- AGP 8.7.3, Gradle wrapper 8.10.2, Kotlin 2.0.21, compileSdk/targetSdk 35, minSdk 24 (минимум MediaPipe).
- `com.google.mediapipe:tasks-vision:1.0.0`, CameraX 1.5.3 (1.6 требует compileSdk 36).
- UI на Views (PreviewView + свой OverlayView), без Compose. Только портретная ориентация.
- Package: `io.github.shantrapa.motion`.

### Структура
```
android/
  settings.gradle.kts, build.gradle.kts, gradlew
  app/src/main/java/io/github/shantrapa/motion/
    MainActivity.kt   # CameraX, разрешения, главный цикл, переключатели (аналог __main__ + capture)
    Config.kt         # все параметры
    Contract.kt       # Landmark, PoseFrame, HandsFrame, индексы, связи
    Geometry.kt       # зеркало, пересчёт в координаты View, центры рук, удержание, сопоставление кистей
    Smoothing.kt      # One Euro Filter
    Metrics.kt        # FPS и задержка
    Tracker.kt        # MediaPipe Pose/Hand Landmarker → контракт
    OverlayView.kt    # всё рисование (аналог renderer)
  app/src/test/...    # JUnit, те же случаи, что в tests/*.py
  app/src/main/assets/  # модели .task, качаются Gradle-задачей, в .gitignore
```

### Правила
- `com.google.mediapipe` импортируется только в `Tracker.kt`; рисование только в `OverlayView.kt`; CameraX только в `MainActivity.kt`.
- `Config`, `Contract`, `Geometry`, `Smoothing`, `Metrics` — чистый Kotlin без `android.*`, тестируются на JVM.
- Фронтальная камера. Инференс на незеркальном кадре с учётом поворота сенсора; зеркало и пересчёт в координаты View (с учётом обрезки PreviewView `FILL_CENTER`) только в `Geometry`.
- `ImageAnalysis` со стратегией `KEEP_ONLY_LATEST`, формат RGBA_8888: очереди кадров нет.
- `LIVE_STREAM`, callback только конвертирует и сохраняет под lock; отрисовка по `invalidate()` в UI-потоке.
- Метка времени кадра — `SystemClock.uptimeMillis()` при входе в анализатор, строго возрастает.
- Расчёт на GPU (delegate) с откатом на CPU; выбор в `Config`.
- Клавиши ПК заменяются экранными переключателями: скелет (`s`), фильтр (`f`), пальцы (`h`).
- Модели в git не коммитятся, Gradle-задача качает их в `assets` перед сборкой.

### Установка и проверка
- Телефон по USB с включённой отладкой; `gradlew installDebug` или `adb install -r app-debug.apk`.
- Экран проверяется через `adb exec-out screencap -p`: Claude видит результат сам, финальная проверка всё равно за мной.
- Если камера занята другим приложением, FPS падает до единиц — сначала проверить это.

### Этапы Android
Порядок и правило подтверждения те же, что для ПК.

**A0. Каркас.** Gradle-проект с wrapper, запрос разрешения камеры, полноэкранный зеркальный превью фронтальной камеры, FPS анализатора поверх. **Готово, когда:** `gradlew assembleDebug` собирает APK, он ставится через adb; приложение просит доступ к камере, показывает зеркальное видео и FPS; отказ в доступе даёт понятное сообщение без падения; при сворачивании камера освобождается.
